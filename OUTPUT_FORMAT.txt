================================================================================
EdgeCloudSim Thesis Output Format Documentation
================================================================================

This file documents all columns in every output log file generated by the simulator.

================================================================================
1. SUCCESS.log — Tasks that completed (finished with result)
================================================================================

Filename pattern: SIMRESULT_<scenario>_<policy>_<devices>DEVICES_SUCCESS.log

How to read: Each row is ; delimited (semicolon-separated values)

COLUMNS (1-based indexing):

Col 1  | taskId              | int   | Unique task identifier
Col 2  | deviceId            | int   | Which user device sent this task (0-N)
Col 3  | datacenterId        | int   | Always 1003 (GENERIC_EDGE_DEVICE_ID) — IGNORE
Col 4  | hostId              | int   | Which edge server processed it (0-13) — USE FOR RELOCATION
Col 5  | vmId                | int   | Which virtual machine on that host (0-1 if VMS_PER_HOST=2)
Col 6  | vmType              | int   | VM type (not used in thesis, always 1)
Col 7  | taskType            | int   | Service class: 0=URLLC_LIKE, 1=EMBB_LIKE
Col 8  | taskLength          | int   | Workload size in MIPS (million instructions)
Col 9  | taskInputType       | int   | Not used (always 1)
Col 10 | taskOutputSize      | int   | Result data size in bytes
Col 11 | taskStartTime       | float | When task started (simulated seconds)
Col 12 | taskEndTime         | float | When task finished (simulated seconds)
Col 13 | totalNetDelay       | float | All network delays combined (seconds)
Col 14 | WLAN_DELAY          | float | Device→edge server delay (seconds)
Col 15 | MAN_DELAY           | float | Edge→edge backhaul delay (seconds). 0.0 = no backhaul used
Col 16 | WAN_DELAY           | float | Edge→cloud delay (usually 0 for edge tasks)
Col 17 | GSM_DELAY           | float | Mobile network delay (usually 0)

EXAMPLE ROW:
434782;17;1003;0;0;1;0;12;1;1;120.00022426505691;120.00148484338986;6.057833293932807E-5;6.057833293932807E-5;0.0;0.0;0.0

HOW TO USE:
- Response time: Col12 - Col11 (in seconds)
- Compliance: Is response_time ≤ deadline (0.010s for URLLC, 0.100s for eMBB)?
- Relocation tracking: Same deviceId (Col2) switching between different hostIds (Col4)
- Backhaul usage: Count rows where Col15 (MAN_DELAY) > 0

================================================================================
2. FAIL.log — Tasks that were rejected/failed
================================================================================

Filename pattern: SIMRESULT_<scenario>_<policy>_<devices>DEVICES_FAIL.log

How to read: Each row is ; delimited

COLUMNS (1-based indexing):

Col 1-12 | (same as SUCCESS.log)    | Base task info (taskId through taskEndTime)
Col 13   | failureReason            | Why the task failed — see legend below

FAILURE REASON CODES:
1 = VM overload (server CPU/memory full)
2 = Network bandwidth rejected (at submission time)
3 = Unfinished due to bandwidth (failed mid-transmission)
4 = Unfinished due to mobility (device moved, server unreachable)
5 = WLAN coverage lost (device left coverage area)
0 = Other/unknown

HOW TO USE:
- Count failures per taskType (Col7)
- Group by failureReason (Col13) to see what killed most tasks
- At collapse point, bandwidth and mobility failures dominate

================================================================================
3. LOCATION.log — Device distribution over time
================================================================================

Filename pattern: SIMRESULT_<scenario>_<policy>_<devices>DEVICES_LOCATION.log

Format: One row per checkpoint (every 6 simulated seconds)

How to read: Each row is ; delimited

COLUMNS (1-based indexing):

Col 1  | time      | float | Checkpoint time (simulated seconds): 12.0, 18.0, 24.0, ... 294.0
Col 2  | dc0_count | int   | How many devices at datacenter 0 at this time
Col 3  | dc1_count | int   | How many devices at datacenter 1 at this time
Col 4  | dc2_count | int   | How many devices at datacenter 2 at this time
... (continue for all 14 datacenters) ...
Col 15 | dc13_count| int   | How many devices at datacenter 13 at this time

EXAMPLE ROW:
12.0;13;15;20;24;14;17;21;18;22;14;22;21;17;12

Means: at time 12 seconds, DC0 has 13 devices, DC1 has 15 devices, DC2 has 20, etc.

Note: Sum of all counts ≈ number of mobile devices (small variance due to rounding)

HOW TO USE:
- Plot over time to see load balance (are devices spread evenly?)
- Ideally, counts stay roughly equal across all datacenters

================================================================================
4. URLLC_LIKE_GENERIC.log — Summary statistics for URLLC tasks
================================================================================

Filename pattern: SIMRESULT_<scenario>_<policy>_<devices>DEVICES_URLLC_LIKE_GENERIC.log

Format: 6 rows (if just URLLC), 5 rows (if all tasks). Each row has ; delimited columns.
Each row represents a DIFFERENT statistic (they are not a table - each row is independent!)

ROW 1 (basicResult) - 14 COLUMNS - Overall task results:
  Col 0 = completed tasks (count)
  Col 1 = total failed tasks (count)
  Col 2 = uncompleted tasks (count)
  Col 3 = failed due to bandwidth rejection
  Col 4 = average service time (seconds)
  Col 5 = average processing time (seconds)
  Col 6 = average network delay (seconds)
  Col 7 = (unused)
  Col 8 = average cost
  Col 9 = failed due to VM capacity overload *** KEY FOR THESIS ***
  Col 10 = failed due to mobility *** KEY FOR THESIS ***
  Col 11 = average QoE metric 1
  Col 12 = average QoE metric 2
  Col 13 = failed due to WLAN coverage loss *** KEY FOR THESIS ***

ROW 2 (edgeResult) - 9 COLUMNS - Tasks that ran on EDGE servers only:
  Col 0 = completed on edge (count)
  Col 1 = failed on edge
  Col 2 = uncompleted on edge
  Col 3 = (unused)
  Col 4 = average service time (edge only)
  Col 5 = average processing time (edge only)
  Col 6 = (unused)
  Col 7 = edge VM load
  Col 8 = failed due to VM capacity (edge)

ROW 3 (cloudResult) - 9 COLUMNS - Tasks that ran on CLOUD (usually 0 for edge workload):
  Col 0 = completed on cloud
  Col 1 = failed on cloud
  Col 2 = uncompleted on cloud
  Col 3 = (unused)
  Col 4 = average service time (cloud only)
  Col 5 = average processing time (cloud only)
  Col 6 = (unused)
  Col 7 = cloud VM load
  Col 8 = failed due to VM capacity (cloud)

ROW 4 (mobileResult) - 9 COLUMNS - Tasks on MOBILE devices (not used in thesis):
  (Same structure as rows 2 and 3)

ROW 5 (bandwidthResult) - 8 COLUMNS - Network delays and bandwidth failures *** KEY FOR THESIS ***:
  Col 0 = average LAN delay (milliseconds)
  Col 1 = average MAN delay (milliseconds) *** measures backhaul congestion ***
  Col 2 = average WAN delay (milliseconds)
  Col 3 = average GSM delay (milliseconds)
  Col 4 = failed due to LAN bandwidth
  Col 5 = failed due to MAN bandwidth *** KEY - backhaul is the bottleneck ***
  Col 6 = failed due to WAN bandwidth
  Col 7 = failed due to GSM bandwidth

ROW 6 (performanceResult) - 2 COLUMNS - Orchestrator performance (only in ALL_APPS file):
  Col 0 = total simulation time (minutes)
  Col 1 = average orchestrator overhead (seconds)

HOW TO USE:
- Use ROW 1 (basicResult) for failure counts:
  - Col 0 = total succeeded
  - Col 1 = total failed
  - Col 9 = how many failed due to VM overload
  - Col 10 = how many failed due to mobility
  - Col 13 = how many failed due to WLAN loss
- Use ROW 5 (bandwidthResult) for network bottleneck:
  - Col 5 = how many failed due to MAN (backhaul) bandwidth
  - If Col 5 is highest failure reason, MAN is the bottleneck
- Compare ROW 1 between CENTRALIZED vs DECENTRALIZED

5. EMBB_LIKE_GENERIC.log — Summary statistics for eMBB tasks
================================================================================

Filename pattern: SIMRESULT_<scenario>_<policy>_<devices>DEVICES_EMBB_LIKE_GENERIC.log

Format: Identical to URLLC_LIKE_GENERIC.log but for eMBB task class only

================================================================================
6. ALL_APPS_GENERIC.log — Summary statistics for all tasks (URLLC + eMBB COMBINED)
================================================================================

Filename pattern: SIMRESULT_<scenario>_<policy>_<devices>DEVICES_ALL_APPS_GENERIC.log

Format: Identical to URLLC_LIKE_GENERIC.log, but numbers are SUMMED

IMPORTANT: "Aggregated" means ALL NUMBERS ARE ADDED TOGETHER

Example:
  URLLC completed = 677,020 tasks
  eMBB completed  = 82,256 tasks
  ALL_APPS completed = 677,020 + 82,256 = 759,276 tasks ← THEY ADD UP

  URLLC failed = 16 tasks
  eMBB failed  = 9 tasks
  ALL_APPS failed = 16 + 9 = 25 tasks ← THEY ADD UP

All columns work the same way - every number in ALL_APPS is URLLC column + eMBB column

WHY 3 FILES?
- URLLC_LIKE_GENERIC.log → Results for FAST tasks only (10ms deadline)
- EMBB_LIKE_GENERIC.log → Results for SLOW tasks only (100ms deadline)
- ALL_APPS_GENERIC.log → Combined results (all tasks together)

You need all 3 to see if each service class performed differently

================================================================================
7. VM_LOAD.log — Virtual machine utilization (debugging only)
================================================================================

Filename pattern: SIMRESULT_<scenario>_<policy>_<devices>DEVICES_VM_LOAD.log

Format: Snapshot of each VM's CPU/memory usage at checkpoints

HOW TO USE:
Optional — for diagnosing if VMs are the bottleneck (not needed for thesis metrics)

================================================================================
QUICK REFERENCE: Which File For Each Metric?
================================================================================

Metric                    | Read from         | How to calculate
--------------------------|-------------------|----------------------------------
Compliance %              | SUCCESS.log       | Count(endTime - startTime ≤ deadline) / total tasks × 100
Failure %                 | FAIL.log          | Count(FAIL rows) / total tasks × 100
Failure reason breakdown  | *_GENERIC.log     | Extract row 2, columns for each reason type
MAN-hop %                 | SUCCESS.log       | Count(MAN_DELAY > 0) / completed tasks × 100
Relocation count          | SUCCESS.log       | Track deviceId (col2) switching hostIds (col4)
Load balance              | LOCATION.log      | Std dev of device counts across datacenters

================================================================================
PYTHON REFERENCE (0-indexed array access)
================================================================================

SUCCESS.log:
  taskId       = parts[0]
  deviceId     = parts[1]
  datacenterId = parts[2]
  hostId       = parts[3]
  vmId         = parts[4]
  vmType       = parts[5]
  taskType     = parts[6]
  taskLength   = parts[7]
  taskInputType= parts[8]
  taskOutputSize=parts[9]
  taskStartTime= parts[10]
  taskEndTime  = parts[11]
  totalDelay   = parts[12]
  wlanDelay    = parts[13]
  manDelay     = parts[14]
  wanDelay     = parts[15]
  gsmDelay     = parts[16]

FAIL.log:
  (Same as SUCCESS.log columns 0-12, then:)
  failureReason = parts[12]

LOCATION.log:
  time = parts[0]
  dc0  = parts[1]
  dc1  = parts[2]
  dc2  = parts[3]
  ... etc
  dc13 = parts[14]
